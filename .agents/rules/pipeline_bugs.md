Found while auditing the `bewo_m2_2026-07-07` run (587 split events) for whether `review_crops/*/verdict.txt` matches `events.csv`:

1. **`classification_source` mislabeling (bug, `src/review.py:359`):** hardcoded to `"claude"` regardless of which backend (`claude` or `gpt`, selectable via `--vision-backend`) actually ran. Confirmed via cost math that the bewo_m2 run actually used GPT-5-mini (Azure OpenAI), not Claude Haiku — `summary.json`'s `estimated_cost_usd` matches gpt-5-mini pricing exactly, not Claude's. Every row in that run's CSV falsely says `classification_source=claude`.

2. **GPT confidence-floor opacity:** `min_gpt_confidence=0.85` (`src/review.py:351`) silently downgrades GPT "real" verdicts below that self-reported confidence to `false_positive`/`confidence=0.0` in the final CSV. `verdict.txt` is written *before* this downgrade, so it retains the raw verdict — meaning `events.csv`'s `claude_confidence` for these events is POST-floor, not the model's raw output. Confirmed on bewo_m2: 280/587 events hit this exact path, 100% with raw confidence 0.66–0.84 (below the 0.85 floor). The 0.85 floor itself was tuned on a different 180-candidate spike baseline (2026-07-06/07), not on bewo_m2.

3. **Silent fail-open gap:** 80/587 review_crops folders have crop images but no `verdict.txt` — the API call itself threw (timeout/bad JSON/etc.), caught by the outer exception handler in `review_ambiguous._call`, which fails open as `verdict=real` at the tracker's raw persistence score with no ACD/anomaly classification. 13.6% of unique split points on this run bypassed real model review this way, silently.

4. Minor: ~24 events have an em-dash → replacement-character (`�`) corruption in `verdict.txt`'s notes text (not present in the CSV's copy of the same text) — cosmetic encoding artifact, same family as the earlier-fixed commit `158e932` ("Fix Windows cp1252 crashes on non-ASCII Claude output"), not fully closed.

**Why:** [[project-cell-split-counter]] — this affects hyperparameter tuning: tuning against `events.csv`'s `claude_confidence` for a GPT-backend run means tuning against an already-floored value, not the model's raw confidence, and the source-of-truth confusion (claude vs gpt labeling) could silently mislead future analysis or the researcher review if not corrected.

**How to apply:** None of these were fixed — flagged for the maintainer to decide when/whether to address. If asked to fix: (1) pass `backend` through to `classification_source` instead of hardcoding, (2) consider logging raw pre-floor confidence into the CSV as its own column so verdict.txt isn't the only place it exists, (3) consider whether fail-open events should be flagged distinctly in the CSV (e.g., a `review_error` flag) rather than blending into normal "real, tracker-confidence" rows.
