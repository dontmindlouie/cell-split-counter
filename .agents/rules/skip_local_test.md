For a small, low-risk change (e.g. renaming one output path string), skipping a local end-to-end test and validating directly via a cheap real run (e.g. a cloud smoke test) is fine — not a process gap to flag or apologize for.

**Why:** During [[project_cell_split_counter]] (2026-07-03), a `debug/crops` → `review_crops` folder rename was validated only via a cloud smoke test run, not a local run first — inconsistent with earlier same-session practice (ND2 ingestion, batching benchmark) where local-first was used. When flagged as a possible process inconsistency, user said "no, i liked what you did" — an explicit confirmation, not a correction. Local testing had also been genuinely unreliable that session (unrelated system memory pressure breaking even small local GPU benchmarks), making a cheap cloud check the more pragmatic validation path anyway.

**How to apply:** Don't treat "always test locally before cloud" as a hard rule. Match validation effort to risk/cost: a one-line/low-blast-radius change earns a cheap real-environment check; a bigger or riskier change (new ingestion path, algorithm change, batching logic) still earns local validation first when that's actually reliable to run. If local testing is known to be flaky in the current environment, defaulting to the cheapest reliable validation (even if that's a cloud run) is the right call, not a corner cut.
