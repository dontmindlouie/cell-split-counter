Never create a directory junction/symlink pointing at real shared data, then run a recursive-delete tool (`git worktree remove`, `rm -rf`, etc.) on something containing that junction, without first testing whether that specific tool follows the junction or correctly unlinks it.

**Why:** On 2026-07-07, while consolidating raw video files for [[project_cell_split_counter]], created a directory junction `cell-split-counter-classify-fix/data/raw` → the main worktree's `data/raw` (to avoid duplicating huge raw files across git worktrees, per the maintainer's explicit request). Then ran `git worktree remove cell-split-counter-classify-fix`. The removal recursed *through* the junction instead of just deleting the reparse point, destroying the real files at the target: a validated 103MB baseline video and an 11.8GB unrelated acquisition. The baseline was recoverable only because a separate Desktop copy existed, verified byte-identical via pixel-diff against cached frame extractions that survived. The 11.8GB file was not recovered (out-of-scope/unvalidated data, so not a concern).

**How to apply:**
- Before pointing a junction/symlink at shared data and then deleting a container of it, test the exact deletion path (worktree remove, rm -rf, whatever tool) on a disposable dummy junction → empty scratch folder first. Confirm the target survives before trusting the pattern on real data.
- If skipping the test isn't an option, manually unlink the junction first (e.g., `Remove-Item path -Force` in PowerShell targets just the reparse point) *before* running the recursive-delete step on its parent.
- For irreplaceable source data specifically, keep a lightweight checksum manifest (see `data/raw/CHECKSUMS.md` in this project, added after this incident) so a candidate recovery/backup file can be verified as genuinely identical in seconds, not just by filename/size.
- This wasn't caught by asking for confirmation beforehand — the destructive step (`git worktree remove`) didn't look risky on its face; the risk was in the *interaction* with something set up minutes earlier. Watch for this pattern generally: a sequence of individually-reasonable actions where an earlier one changes the blast radius of a later one.
